# 07 从归因到行动

分析结束时应留下可复查的诊断记录：问题发生在哪个阶段、现有证据支持什么、哪些解释已被排除，以及下一轮应该验证哪类候选。`inspect`、`optimize`、`validate` 与 `revert` 描述当前分析应做什么；候选的 `accept`、`tune`、`reject` 描述后续性能优化中的具体判断。

## 用证据决定行动

| 状态 | 需要具备的证据 | 输出 |
|:---|:---|:---|
| `inspect` | 现象存在，但指标或工作负载还不完整 | 补测字段与待验证假设 |
| `optimize` | 时间线、驻留或资源上界已指向主约束 | 候选类别、预期收益与需复测的代价 |
| `validate` | 固定条件下的对照显示稳定收益，守护指标未越界 | 适用工作负载、复测记录与限制 |
| `revert` | 候选无收益、引入回归或无法复现 | 回退原因与下一条假设 |

## 最小结论记录

性能优化需要的是诊断记录，而不是孤立截图、热点名称或一串工具输出。证据不足时保留待验证假设，不提前指定优化方案。

| 字段组 | 必须保留 | 交给性能优化的作用 |
|:---|:---|:---|
| 问题身份 | 现象、阶段、目标指标、工作负载与环境 | 保持候选复测条件不变 |
| 证据引用 | 基线分布、执行轨迹、对象驻留、性能剖析和结果路径 | 允许复查原始证据，不复制整份输出 |
| 当前归因 | 时间 / 驻留证据、主约束、判别实验、反例与未解释现象 | 限定候选机制和证伪条件 |
| 守护条件 | 正确性、质量、失败率、容量、SLO 与回归阈值 | 阻止局部收益掩盖退化 |
| 行动状态 | `inspect`、`optimize`、`validate` 或 `revert` | 决定补测、选候选、组合复测或回退 |

## 交付诊断记录

完成上述记录后，进入[性能优化专题](../performance_optimization/intro.md)把主约束转成候选并进行配对复测。单项与组合复测同时检查端到端指标、守护条件与回退方案；多卡归因转入[通信与并行专题](../communication_parallelism/intro.md)补齐真实拓扑与每个进程的记录。
